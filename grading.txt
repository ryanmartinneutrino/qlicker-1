Grading notes:

- We want to implement the grades system in a very similar way to the meteorjs version of the app, start with consulting that. Any work that is done has to maintain compatability with the legacy database since when we go to production, we will migrate using the running database. 

- In general, follow the implementation in the meteorjs version of the app. The main change is that we'll integrate the "grading page" for instructors as a tab in the Review Session page for instructors rather than having a separate grading page. 

- Assume that more question types will be added in the future, so think about this during implementation. 

- Each student has a grade object associated with a session, from there, one can obtain the participation grade and the grade for the session. These are out of 100% and correspond to the total number of points that they obtained out of the total number that was available. Again, follow the meteorjs version to understand this precisely.

- Each question can be assigned a certain number of points. If the student answers correctly for that question, they get the number of points for that question (marks). These are labeled as "marks" in the grade item, as each question in the session contributes marks to that grade. 

- If a question has zero points associated to it, it does not get included in the grade calculation (adds 0 out of 0), including the participation. So if a session has 10 questions worth 0 points and one question worth 1 point, student gets full participation (100%) if they answered that one question, and full grade value for the session if they answered that question correctly. 

- Generally, when autograding an interactive session, if a question has a single attempt and fewer responses than 10% of the number of people that joined the session, then it should not be counted in grading (towards participation or correctness - essentially treating that question as if it had zero points). 

- Some questions (MC/MS/TF/NU) can be graded automatically. For now, only SA cannot be graded automatically, but that could change if we add additional types.

- We will do the automatic scoring the same way as in meteorjs for all these questions except for MS. For MS, there are different ways to score these. Make it a session option to choose how MS questions will be scored. Options are A) All or nothing (default - either they get the exact selection of options for a mark, or zero marks, and this multiplies the number of points the question is worth - I think this is the way it's done in meteorjs), B) Right minus wrong (the score is the fraction of options they chose correctly multiplied by the number of points the question is worth). Do a quick google search for any other ways to score multiple select type questions. Make sure there's a useful tooltip that explains the calculation. The default method should be the method used in the meteorjs version, if I incorrectly described that as A, then fix it. 

- We need a grade table (add this as additional tabs (pages?) from the course manage page (prof) or course page (student). Student should never be able to see grades from other students, make sure this is implemented in the backend. We want to see a table with all grades, one row per student, where sessions are columns (and have participation and correct). The table is sortable, searchable (by student name or email), and one can select with sessions are being showed. There is a way to click on a session header to go to the review page for that session. Each session has a button to recalculate grades. Clicking on a grade in the table pulls up a modal with details about that grade item, allowing manual overrides of the grades that are not re-written if an automatic grade re-calculation is triggered. This should all follow the implementation in meteorjs pretty closely, although it shoudl be cleaner. If an automatic grade calculation results in a different mark for a particular question, then the user should receive a warning with a list of all the students and corresponding marks that were not updated because they were already manually entered. Any grade (or mark) that was entered manually needs a manual override to be changed. The modal that presents the list of users and question marks that differ should have some buttons to easily accept or reject the updated automatic marks (per student or all at once). 

- There is a CSV button to download all of the of grade data, this should download the same information as one would get from the meteorjs version. Choosing which columns are displayed, chooses which columns end up in the CSV. There is button to choose all sessions.

- Make sure that MIGRATION.md describes progress and details the grade calculation. We need to start writing documentation for everything (user and dev manuals). The grade calculations need to go into the documentation. Start thinking about this documentation and create a starting point. 

- When setting a session to reviewable, it automatically triggers grades to be calculated if they don't already exist for that session (if checks that all students have grade items and if only a few are missing, it fills the grade items for them as well). Making a session reviewable only triggers the grade calculation for students that don't have a grade item for that session, in such a way that all students, even those that didn't join, have a grade item for the session. After that, there is a button in the session review (e.g. under the grading tab/panel) that allows "Re-calculate all grades". User receives a warning anytime an automatic grade calculation is run for which there are questions that cannot get graded automatically (currently, if a session contains SA questions, but in the future, there may be other question types that cannot be graded automatically, so don't just check for the presence of an SA, check for the presence of grades that can't be calculated automatically. 

- Thus, user receives a warning when making a session reviewable if it has questions in it that have not been graded yet because they can't be graded automatically. If all questions are graded, then no warning and the session can be made reviewable. We want to avoid students seeing questions that haven't been graded. 

- If a session is not reviewable, then it does not show up in the grade table for a student. 

- The grading interface should closely follow the implementation and functionality of that in the meteorjs app, aside from being access through the review session. If a session needs grading, it should be indicated with a chip (only for profs) that shows how many questions are ungraded (and for how many students).  

- The grading interface should allow one question to be graded a time. It should easily allow students to be searched (autocomplete search for name and email), and we will later add the ability to search students based on their group (groups are not implemented yet, they come in the next phase of migration). The interface should show a table, where each row is a student and their answer. The table should have columns for student name and email, their reponse, a text box that instructors can write in as feedback (editable, make it a tiptap box with all the same functionality as the other tiptap boxes, including math and a live preview), and the marks they got for that question (editable). In the student session review, it should be obvious when they've received feedback for a question and they should be able to easily see that feedback. In the meteorjs version it's quite hidden and students never see the feedback. One should have the ability to filter the table based on specific responses and also have the ability to bulk edit questions that are filtered (e.g. to assign them all the same marks and/or feedback). 

- It should be obvious in the grading interface what still needs grading. Maybe there could be a ribbon at the top that shows all the questions and highlight in green/red whether they need to be graded, and that can be clicked so that the table shows response data from that question. This could be how one navigates/cycles between questions. If there are multiple attempts, the grading interface only ever shows the highest attempt number. The grading interface also shows the question and the correct answer, with option to expand and show the solution. 

- Again, the grading interface in meteorjs has good functionality, it just needs to be prettier. Make everything consistent with the style choices that have been made. 

- Make sure to update MIGRATION.md with progress.
