We are going to add groups functionality to the app, closely following the approach taken in the meteorjs version of the app. Below are some notes on groups:

- Review MIGRATION.md and CODING_STANDARDS.md to get context and ensure alignment with what has been done. Also review how groups are handled in the meteorjs app and ensure that there will be backwards compatability loading the app from a legacy database. Keep MIGRATION.md and any other documentation up to date (in particular for the api).

- A course can have multiple categories of groups. An instructor starts by creating a new category (specifying its name and the number of groups it contains) and then adds students to the groups. Students can only be in one group in a particular category. 

- Just like in the meteorjs version, the makeup of groups can be downloaded as CSV (use the same format). However, we also want to be able to upload a CSV (when doing so, user still specifies the name of the category). 

- We need an interface to manage groups in the course. I would suggest adding another tab on the course manage prof page. 

- The interface for managing groups should function in a similar way as the one in meteorjs. Namely, it should be easy to navigate categories and create new ones. Within a category, it should be easy to navigate between groups and change their names (default Group 1, Group 2, etc). It should be easy to add and remove students from groups (as in the meteorjs version). For example, one should be able to select a category and group, then easily see the students in that group as well as a list of students that are not currently in a group. Clicking on a student in the selected group removes them, clicking on a student not currently in a group adds them to the selected group. The list of students not in a group can be changed into a list of students already in a group (to see if a particular student is already assigned a group). When showing the list of students already in a group, clicking on a student sets that group as selected (this makes it easy to know which groups particular students are in). The list of students (in or not in a group) should be searchable based on name and email. Make sure the search box doesn't block each time a character is entered, make it snappy. 

- In the above, students appear in lists (the group they're in, or the general list if not in a group for that category). You should make a reusable react component for showing a student in a list, the component should have name, email, and a clickable avatar that brings up a big picture. Clicking anywhere else on the student may or may not result in an action (in the bullet point above, the action moves students in and out of a group). Use this component in all places were we list students in the web UI so that we have a consistent view of a student name with a picture. I would show email on a second line, greyed out. You can implement this to look like the list of students in the course manage page (Students tab), and then use it there. Currently, in the course manage page, there is a button on that student list item to remove the student from the course. Instead, make it the action that clicking on the student brings up a modal that shows some info about the student (e.g. average participation, etc) and also gives a button to remove the student from the course (which still requires a confirmation). 

- In the grading interface of a prof session review, we need to add functionality to show only students in a particular group (so need dropdowns for the category and the group within).
